# Security and threat review

This page records the controls in Aahaarloop, the checklist used for [#70], and
the residual risks that remain. Security is shared across the API foundation
([API foundation](./api-foundation.md)), [authentication](./authentication.md),
[role-based access](./rbac.md), [moderation](./moderation.md) and
[telemetry](./telemetry.md); this page ties them together.

## Threat summary

| Threat | Control | Where |
| --- | --- | --- |
| Stolen session / account takeover | Google OAuth, JWT sessions, server-provisioned identity, `AUTH_SECRET` | [Authentication](./authentication.md) |
| Cross-tenant data access (IDOR) | Organization-scoped services and server-side role guards on every protected route | `apps/web/src/lib/auth/guards.ts`, [RBAC](./rbac.md) |
| Cross-site request forgery | `Origin`-header check on all unsafe API methods (`POST`/`PUT`/`PATCH`/`DELETE`) | `apps/web/src/lib/security/csrf.ts`, `withApiHandler` |
| Clickjacking / MIME sniffing / referrer leaks | Security headers on every response | `apps/web/src/lib/security/headers.ts`, `next.config.ts` |
| Malicious uploads | Allowlisted MIME types, 8 MiB cap, server-side signed uploads with a server-only secret | `apps/web/src/lib/uploads/cloudinary.ts`, [ADR-0008](./adr/0008-cloudinary.md) |
| Spam / brute force | Per-client rate limiters (report submissions, upload signing) and idempotency keys | `withApiHandler`, `apps/web/src/lib/api/rate-limit.ts` |
| Secret leakage | Redacted audit logs and error envelopes; static secret scan in CI | `scripts/security-audit.mjs`, [telemetry](./telemetry.md) |
| Supply-chain compromise | Frozen lockfile, pinned actions, audit of dependency specs and registry URLs | `scripts/security-audit.mjs`, [CI](./ci.md) |

## Security checklist

- [x] Input validation on every API body and query (`zod` schemas via
      `withApiHandler`).
- [x] Upload validation: MIME allowlist, byte-size cap, server-side signature;
      the Cloudinary API secret never reaches the client.
- [x] Authorization: admin, organization and ownership guards verified on all
      protected routes; cross-tenant reads/edits/publishes rejected.
- [x] Rate limiting on abuse-prone endpoints (reports, upload signing).
- [x] CSRF protection via `Origin` matching for state-changing requests.
- [x] Security headers, including HSTS in production, on every response.
- [x] Secret audit: tracked files scanned for high-confidence secret shapes;
      dependency specs and registry URLs checked.
- [x] Dependency audit: `pnpm audit` run periodically (see below).
- [x] IDOR and abuse tests pass (`apps/web/test/security-hardening.test.mjs`).
- [x] APK checksums and install notes generated by the
      [release workflow](./apk-release.md).
- [x] Residual risks documented below.

## Running the audits

```sh
node scripts/security-audit.mjs   # static secret + dependency scan
pnpm audit                        # published CVEs in the dependency tree
pnpm test                         # includes the security-hardening tests
```

The static scan examines all tracked files, skips lockfiles and placeholders,
and reports findings without printing the matched secret value. It fails the
build on any high-confidence finding. `pnpm audit` is a manual periodic check
(weekly and before each release); the pinned lockfile keeps it reproducible.

## Residual risks

- **In-memory stores.** Demo/matching/telemetry stores are in memory and reset
  on restart. They are not a durable data store; production uses the database
  described in [database schema](./database/schema.md).
- **In-memory rate limiter.** Counters are per-process and not shared across
  instances; use a shared store (e.g. Redis) before horizontally scaling.
- **Spoofable proxy headers.** The rate-limit key may use `x-forwarded-for`,
  which a client can spoof unless the ingress overwrites it. Terminate traffic
  at a trusted proxy that sets this header.
- **No WAF / bot management.** There is no web application firewall or advanced
  bot detection; rate limiting is the only abuse control today.
- **CSRF via missing Origin.** Non-browser clients send no `Origin` and are
  allowed by design (the mobile app needs this). Their requests rely on the
  session/JWT and server-side authorization instead.
- **Internal APK distribution.** The Android APK is shared via GitHub Releases,
  not the Play Store; install integrity depends on the published SHA-256 and
  the recipient verifying it. Device testing is a manual release step
  ([APK release](./apk-release.md)).
- **Third-party trust.** Google (OAuth) and Cloudinary (uploads/storage) are
  trusted services; their availability and security posture are outside this
  repository's control.
- **Physical-device testing.** There is no automated device/emulator test in
  CI; the donor/recipient flows must be exercised on a real phone before a
  release is signed off.
- **HSTS only in production.** Local development intentionally omits HSTS so
  plain-HTTP testing works.
- **CVE lag.** `pnpm audit` reflects published advisories at the time it runs;
  a zero-day or unpublished issue is not detected by any scan here.

## Reporting a vulnerability

Do not open a public issue for a suspected vulnerability. Contact the
maintainers privately with reproduction steps and impact; fixes and a
coordinated disclosure are handled before a public issue is created.
